# Model residency and wait phases — 1.8.3

## Behavior and scope

- Each connection has maxResidentModels (integer 0–128; default 0/unlimited) and modelWaitPolicy (capacity/default or serial), editable in Connection settings.
- A positive limit enables managed loading even with global On demand off. Model preparation is serialized per normalized server root. Connections to the same root use the strictest positive limit and serial setting. Config changes affect newly started jobs; saving a lower limit does not immediately unload existing models.
- Capacity mode permits concurrent jobs for loaded models, and waits if a cold request cannot evict an idle model. Serial mode waits for every other job using the same server, including tool/user-input waits.
- SQLite migration 7 stores cumulative admitted-job counts and last-use times. Eviction ranks idle models by LFU, then oldest last use, then stable identifier. Aliases resolve the base model and share both usage and activity; multiple instances count toward the residency limit and are unloaded as one model group.
- Active jobs retain a model lease until completion/error/stop. Cancelled queued requests do not load models later. Dispatched load/unload mutations retain the server lock until they settle to avoid concurrent replacement against uncertain state. Subsequent inventory checks verify unload/load outcomes. Busy unload responses wait rather than loading over the limit.
- LM Studio native inventory/load/unload APIs are supported, including when the connection driver is OpenAI-compatible. Existing /api/inference management remains a fallback. Servers without a supported model-management API fail with an actionable error when a positive cap is requested; unlimited ordinary OpenAI chat remains supported.
- Automatic activity protection covers this application's users/jobs. External clients are only observable when upstream exposes busy metadata or rejects busy unloads. Administrator-triggered manual unload remains allowed during generation.
- Snapshots carry transient waitPhase values: waiting-session, freeing-space, loading-model, waiting-server, preparing-response. These are localized in the assistant response area with a status role and spinner; they are not persisted as message content and clear at job termination.
- Five seconds without upstream progress shows waiting-server. Connection refusal/DNS errors retry for at most 30 seconds and remain cancellable. Ambiguous inference failures are not replayed. Model mutations have five-minute bounds; inventory reads have 30-second bounds.
- OpenAI-compatible streams do not expose exact Prefill lifecycle events. Preparing response represents the request-to-first-output preparation interval, with delayed activity reported as server waiting.
