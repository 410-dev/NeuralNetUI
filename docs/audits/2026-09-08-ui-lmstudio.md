## 점검 범위와 검증 환경

Next.js 페이지/설정 UI, 연결·모델·별칭·추론 프리셋, 채팅 스트림·작업 관리·대화 저장, 인증/설정 권한, 첨부 및 웹 도구의 주요 경로를 검토했다. 설치 프로그램과 Android 앱은 이번 실행 검증 범위에 포함하지 않았다.

브라우저 플러그인으로 로그인, 모델 편집, 연결 편집, 별칭 변경 및 저장, 후속 채팅, 선택형 질문 오류, 설정 키보드 조작을 검사했다. 1280×900 데스크톱과 390×844 모바일 뷰포트를 확인했다. 모바일 설정에서 페이지 전체의 가로 넘침은 관찰되지 않았다. 실제 휴대폰의 터치·가상 키보드 동작은 검증하지 않았다.

앱은 `127.0.0.1:3107`, 모의 추론 서버는 `127.0.0.1:3108`에서 실행했다. 테스트 DB는 `%TEMP%/neuralnetui-audit-20260908`에 분리했다. 아래 삭제·키 변경·사용자 생성 실험은 모두 이 테스트 데이터에만 수행했다. 실제 사용자 대화와 연결 설정은 편집하지 않았다.

실제 로컬 LM Studio의 `GET /api/v1/models` 응답을 조회해 `key`, `capabilities.reasoning.allowed_options`, `loaded_instances`, `selected_variant` 형식을 확인했다. 실제 모델 로드·언로드·추론은 실행하지 않았다. 모델 응답·오류·동시성 실험은 모의 서버 또는 주입한 fetch로 진행했다.

검증 결과:

- `npm test`: 46/46 통과.
- `npx tsc --noEmit`: 통과.
- `npm run build`: 통과.
- 별도 lint 스크립트/설정이 없어 lint 실행 결과는 없다. 타입 검사와 lint는 구분한다.
- 브라우저 검사 종료 시 수집한 error/warn 콘솔 로그는 비어 있었다. 오류 응답 실험에서 앱이 오류를 삼키는 문제는 별도로 재현됐다.
- 기존 테스트 통과는 아래 통합 경로의 정상 동작을 보장하지 않는다.

## P1 — 우선 수정

### 1. 일반 사용자의 설정 저장이 공통 기본 추론 프리셋을 삭제한다

- 근거: `lib/config.ts:68–76`.
- 재현: 기본 프리셋이 있는 모델 두 개를 준비하고 일반 사용자가 `GET /api/config` 결과를 변경 없이 `PUT /api/config`로 저장한다.
- 실제: 두 모델의 `reasoningPresets: [default]`가 모두 `[]`로 바뀐다. 관리자 계정으로 다시 조회해도 삭제되어 있다.
- 원인: 비관리자 저장 시 builtin 항목을 editable 목록에서 제거하면서, protected 목록에는 다른 사용자의 custom 항목만 남긴다. 이 결과를 전역 연결 모델에 저장한다.
- 수정 방향: 비관리자가 수정할 수 없는 builtin 및 타인 프리셋을 그대로 보존하고, 본인 custom 프리셋만 병합한다. 일반 설정·추론 전송 토글 등 설정 API를 사용하는 모든 경로에 회귀 테스트가 필요하다.

### 2. 별칭의 기반 모델을 다른 서버 모델로 바꿔도 기존 서버로 요청한다

- 근거: `app/page.tsx:1190,1312`, `lib/connection-drivers.ts:35–46`.
- 재현: 연결 A의 모델 a에서 별칭 생성 → 기반 모델을 연결 B의 모델 b로 변경 → 저장.
- 실제: 저장된 별칭이 `sourceModel: audit-model-b`, `connectionId: audit-a`로 남는다. 라우터도 A를 반환한다.
- 영향: 모델 미발견 오류, 잘못된 서버 사용. 서버마다 모델 식별자가 겹치면 의도와 다른 모델이 응답할 수 있다.
- 수정 방향: 기반 모델 변경 시 연결 ID도 함께 갱신한다. 라우터는 명시 연결이 해당 기반 모델과 일치하는지도 검증해야 한다.

### 3. 생성 중인 대화를 삭제하면 대화가 다시 생성된다

- 근거: `app/api/conversations/[id]/route.ts:24–26`, `lib/chat-runtime.ts:94–111`, `lib/conversations.ts:100–104`, `app/page.tsx:480–495`.
- 재현: 느린 모의 응답 시작 → 대화 DELETE → 생성 완료까지 대기.
- 실제: DELETE는 204, 직후 GET은 404인데 생성 완료 후 GET이 200으로 바뀐다.
- 원인: 삭제 API가 작업을 취소하거나 폐기하지 않는다. 작업은 시작 당시 대화 스냅샷을 다시 insert한다. UI 역시 현재 선택된 대화만 중지하므로 다른 대화에서 진행 중인 생성에는 이 문제가 발생한다.
- 수정 방향: 삭제와 작업 취소/폐기를 통합하고, 이미 삭제된 대화를 작업 저장이 되살릴 수 없도록 세대 번호 또는 삭제 상태를 검증한다. 전체 삭제도 동일하게 처리한다.

### 4. 선택형 질문의 사용자 답변이 다음 턴에서 모델에게 전달되지 않는다

- 근거: `app/page.tsx:621`, `lib/chat-runtime.ts:12,125–134`, `lib/conversation-messages.ts:28`.
- 재현: 선택형 답변 `Color? → Blue`가 저장된 대화를 열고 “Which color did I choose?”를 전송한다.
- 실제: 화면에는 Blue 답변이 보이지만 모의 서버가 받은 messages는 `Pick color`, `Saved.`, 후속 질문뿐이다. Blue 및 tool 결과가 없다.
- 영향: 모델이 사용자의 선택을 잊고 재질문하거나 앞선 요구사항과 다른 답변을 한다. 검색·페이지 방문 결과도 다음 턴에는 구조화된 도구 기록으로 유지되지 않는다.
- 수정 방향: 저장된 tool 호출/결과를 유효한 upstream 대화로 복원한다. 최소한 선택형 사용자 답변은 대화 이력에 명시적으로 포함해야 한다.

## P2 — LM Studio 및 연결

### 5. 실제 로드된 컨텍스트 한도를 무시한다

- 근거: `lib/model-context.ts:21–45`, `app/api/models/context/route.ts:49`.
- 재현: `max_context_length: 262144`, `loaded_instances[0].config.context_length: 4096`을 반환한다.
- 실제: 컨텍스트 갱신 API와 UI는 262,144를 사용한다. 현재 인스턴스 한도보다 64배 큰 값이다.
- 원인: 컨텍스트 추론 함수가 최상위 필드만 읽고 `loaded_instances[].config.context_length`를 읽지 않는다.
- 수정 방향: 실제 사용할 인스턴스의 컨텍스트를 선택해 UI와 로드 정책에 함께 반영한다. 이미 로드된 모델에서 설정 한도를 바꿨을 때 재로드 필요 여부도 명확히 해야 한다.
- 형식 근거: [LM Studio 모델 목록 문서](https://lmstudio.ai/docs/developer/rest/list)는 모델 최대값과 로드된 인스턴스 설정값을 구분한다.

### 6. 한 대화의 로딩 취소가 다른 대화의 로딩까지 실패시킨다

- 근거: `lib/lm-studio-control.ts:36–46`.
- 재현: 같은 모델을 서로 다른 AbortController로 동시에 로드 요청하고 첫 요청만 abort한다.
- 실제: 두 Promise 모두 `AbortError`로 reject된다. 두 번째 요청의 signal은 `aborted: false`다.
- 원인: 공유 Promise의 fetch가 첫 요청자의 signal에 종속된다. 반대로 두 번째 요청자가 취소되면 공유 로딩이 끝날 때까지 기다릴 수 있다.
- 수정 방향: 공유 로드 작업과 개별 대화의 대기를 분리한다. 각 대기는 독립 취소하고, 공용 로드를 언제 취소할지는 별도 정책으로 정한다.

### 7. 다른 대화가 생성 중이어도 모델을 언로드할 수 있다

- 근거: `app/page.tsx:420–424,445–451,825`, `app/api/inference/unload/route.ts:10–28`.
- 재현: 모의 모델에서 응답 생성 중 해당 모델의 언로드 API 호출.
- 실제: 200 `{ok:true}`이며 실제 모의 서버로 `POST /api/v1/models/unload`가 전달된다.
- 원인: UI는 현재 화면의 `isGenerating`만 보고, 서버는 실행 중 작업을 검사하지 않는다. 새 채팅으로 이동하면 UI 제한도 해제된다.
- 후속 결정: 최초의 언로드 제한 제안은 적용하지 않는다. 사용자 요청에 따라 서버 부하 완화를 우선해 생성 중에도 언로드를 허용한다.

### 8. 기본 추론 지원을 꺼도 reasoning_effort를 계속 전송한다

- 근거: `app/page.tsx:1339`, `lib/chat-runtime.ts:256,278`.
- 재현: `reasoningSupported:false`인 모델에 기존 `effort:high` 프리셋을 유지하고 요청한다.
- 실제: 모의 upstream 요청에 `reasoning_effort: "high"`가 포함된다.
- 영향: UI에서는 강도 설정이 숨겨지지만 서버에는 이전 값이 계속 전달된다. 파라미터 미지원 모델에서는 오류가 지속될 수 있다.
- 수정 방향: 모델 지원 여부와 선택 프리셋의 유효성을 함께 검사해 요청을 생성한다.

### 9. 저장된 API 키를 제거할 수 없다

- 근거: `lib/config.ts:79`, `app/api/models/detect/route.ts:16`.
- 재현: 테스트용 문자열을 키로 저장 → 빈 문자열로 변경해 저장 → 다시 조회.
- 실제: `hasApiKey:true`가 유지된다. 빈 입력은 항상 기존 키 유지로 해석된다.
- 영향: 인증이 필요 없는 서버로 연결을 바꾸거나 키 사용을 중단할 때도 이전 키가 계속 사용된다.
- 수정 방향: 키 유지·교체·삭제를 구분하는 요청 형식과 UI를 제공한다. 명시적인 삭제 의도만 키를 제거하도록 한다.

## P2 — UI·UX 및 채팅 안정성

### 10. 연결 편집이 저장 전 모델·프리셋 편집값을 버린다

- 근거: `app/page.tsx:1171,1179–1186,1258–1259`.
- 재현: 모델 이름을 `Edited audit model`로 수정 → 연결 탭에서 연결 이름 수정 → 모델 탭 복귀.
- 실제: 모델 이름이 `audit-model-a`로 돌아간다. 브라우저에서 직접 재현했다.
- 원인: 모델 편집은 `draft.models`만 수정하지만 연결 변경은 오래된 `connections[].models`에서 전체 모델 목록을 재생성한다. 재감지에도 유사한 경로가 있다.
- 수정 방향: 모델 설정의 상태 원본을 하나로 만들거나, 연결 목록을 재계산하기 전에 미저장 모델 편집값을 병합한다.

### 11. 선택형 질문을 중단할 수 없고 작업이 사라지면 입력이 막힌다

- 근거: `app/page.tsx:355,568–569,900,920`, `lib/conversation-messages.ts:16–24`, `lib/chat-runtime.ts:207–212,305–308`.
- 재현: 서버 재시작 후 상태에 해당하는 “저장된 waiting 질문은 있지만 메모리 작업은 없는 대화”를 열어 답변한다.
- 실제: “실행 중인 채팅 작업이 없습니다.”만 표시하고 질문·비활성 입력창을 유지한다. 일반 메시지 전송 버튼도 비활성이다.
- 정상 대기 중에도 `pendingChoice`가 stop 버튼까지 비활성화하므로 질문을 취소하는 직접적인 UI 경로가 없다.
- 수정 방향: 질문 중단 버튼을 제공하고, 작업 404/종료 시 남은 waiting 이벤트를 중단 상태로 정리한다. 재생성·분기 등의 우회 없이 입력을 복구해야 한다.

### 12. SSE 내부 오류를 빈 정상 완료로 처리한다

- 근거: `lib/chat-runtime.ts:147–179,280–284`.
- 재현: HTTP 200 SSE로 `{error:{message:"Context length exceeded"}}`를 보내고 종료한다.
- 실제: 앱 SSE는 `status:"completed", content:""`를 반환하며 오류를 사용자에게 알리지 않는다.
- 원인: payload의 error를 검사하지 않고, 유효한 종료 이벤트가 없어도 tool 호출이 없으면 완료로 처리한다. JSON 처리 전체를 catch로 무시하는 것도 오류를 숨긴다.
- 수정 방향: 스트림 error와 정상 종료를 구별하고, 불완전 종료·파싱 실패에 대한 오류 상태를 보존한다.

### 13. 대화 저장 실패를 무시하거나 생성 상태가 풀리지 않을 수 있다

- 근거: `app/page.tsx:388–393,613–616`.
- 검증: 코드 경로 확인. 브라우저 네트워크 장애 주입은 하지 않았다.
- `persist()`는 저장 응답의 `response.ok`를 검사하지 않고 화면 상태부터 바꾼다. 편집·삭제가 서버에서 거부돼도 화면에서는 성공한 것처럼 보일 수 있다.
- 최초 저장의 fetch가 reject되면 `runCompletion()`의 try 바깥에서 예외가 발생한다. 이미 설정한 `isGenerating:true`를 해제하는 catch에도 도달하지 않는다.
- 수정 방향: 저장 응답을 검증하고 실패 시 상태 복구·재시도를 제공한다. 저장부터 생성까지 try/finally로 감싼다.

### 14. 설정 모달의 키보드 포커스가 배경으로 이동한다

- 근거: `app/page.tsx:1216`.
- 재현: 설정 열기 → 마지막 저장 버튼에서 Tab 두 번. `document.activeElement`가 배경의 “새 채팅” 버튼이 된다. Escape를 눌러도 설정은 닫히지 않는다.
- 영향: 키보드 사용자가 설정 중 배경 동작을 실행할 수 있다. 닫기 아이콘과 여러 스위치에도 접근성 이름이 없어 스크린리더에서 의미를 구분하기 어렵다.
- 수정 방향: 모달 내부 포커스 순환, 초기/복귀 포커스, Escape 닫기, 배경 inert 처리, 버튼·스위치 이름을 제공한다.

### 15. 완료·삭제된 채팅 작업이 메모리에 계속 남는다

- 근거: `lib/chat-runtime.ts:56–57,309–310,324–328`.
- 검증: 코드 경로 확인. 장시간 힙 증가량을 계측하지 않았다.
- 전역 jobs Map에 대화별 작업을 추가하지만 완료·중지·삭제 시 제거하거나 TTL로 만료시키는 코드가 없다.
- 영향: 새 대화를 계속 만들면 각 작업의 입력 메시지, 대화 브랜치, 도구 결과가 프로세스 재시작까지 유지된다. DB에서 삭제한 대화의 작업도 API에서 조회 가능한 상태로 남는다.
- 수정 방향: 활성 작업과 짧은 완료 스냅샷 캐시를 분리하고 TTL·크기 제한을 둔다. 대화/사용자 삭제 시 관련 작업도 정리한다.

## 추가 검증 및 사용성 개선 후보

다음은 위 15건과 별도로 취급한다. 실모델 검증 없이 드라이버 오류라고 확정하지 않았다.

- LM Studio native API의 `off/on/low/medium/xhigh` 옵션을 OpenAI 호환 `reasoning_effort`에 그대로 넣는 동작은 실제 설치 버전·모델별 확인이 필요하다. [Chat Completions 문서](https://lmstudio.ai/docs/developer/openai-compat/chat-completions)의 명시 파라미터 목록만으로 모든 reasoning 옵션 지원을 단정할 수 없다.
- 여러 quantization variant 또는 사용자 지정 instance ID가 있을 때 원하는 인스턴스를 정확히 선택하는지 실제 로드 실험이 필요하다. 현재 로드 함수는 응답의 instance ID를 보존하지 않는다.
- on-demand 로딩에는 `model.contextWindowTokens` 원본만 전달한다. 별칭에 표시되는 기반 모델 상속값과 로드 파라미터가 일치하는지, 이미 로드된 모델에서 한도 변경을 어떻게 적용할지 추가 검증이 필요하다.
- 모바일 설정은 모델 목록·에디터·설정 본문에 중첩 스크롤이 있어 긴 설정에서 조작 부담이 크다. 좁은 화면에서 목록 접기 또는 단일 편집 화면을 검토할 만하다.
- 한국어 UI에도 `On demand`, `Tools`, `Optional`, `/api/inference/load` 안내가 남아 있다. LM Studio 연결에 맞는 실제 동작 설명과 자연스러운 번역으로 정리할 필요가 있다.
- API 요청 지연·저장 중 탭 이동, 여러 사용자 동시 설정 저장, 업로드 중 대화 전환은 추가 스트레스 검증 대상으로 남긴다.

권장 수정 순서는 공통 설정 보존(#1), 별칭 라우팅(#2), 삭제/작업 수명주기(#3), 답변 이력(#4)을 먼저 처리하고, LM Studio 상태·취소 처리를 정리한 뒤 UI 상태와 접근성을 보강하는 것이다.
